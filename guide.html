Human Writer / 0.4.1 · 先定标准，一次自查后交稿

使用指南

01 · 安装与更新

当前面向 Codex Desktop / Codex CLI，已有安装验证环境为 macOS、Node.js 24.13.0 与 Codex CLI 0.163.0-alpha.10.2。需要宿主提供 plugins、hooks、MCP 和原生异步问题卡；其他操作系统与宿主未验证。

本页下载为 0.4.1，补充修订保真与来源判断。先确认本篇标准；默认一次自查、一次修改后交稿，不自动再审或弹定稿卡。更新与已知限制。

交给 Codex 安装

  1. 下载 ZIP 和 SHA-256 文件。解压到持久的本机目录。
  2. 把 ZIP 或解压目录交给 Codex，发送下面这段话。
请安装或更新这个 Human Writer 插件。先核验包内 SHA256SUMS，备份现有 Codex 配置和 Human Writer 安装，只修改 Human Writer 相关配置；我授权信任它的 SessionStart 和 UserPromptSubmit 两个 hook。安装后核对版本、技能入口、两个 hook 和 MCP，不创建作品、不改我的稿件。

包内 INSTALL.md 给出步骤。安装工具不自动信任 hook；先查看实际定义和 hash，再按授权运行信任步骤。新安装完成后，在新会话中使用入口。

终端安装与校验

在 ZIP 与校验文件所在目录核对下载，再进入解压目录：

shasum -a 256 -c human-writer-codex.zip.sha256
unzip human-writer-codex.zip
cd human-writer-codex
shasum -a 256 -c SHA256SUMS
codex plugin marketplace add "$PWD" --json
codex plugin add human-writer@human-writer-local --json
node scripts/trust-hooks.mjs --review

仅在同意显示的两个 hook 后，用 review 返回的 token 执行 node scripts/trust-hooks.mjs --approve <reviewToken>。安装目录不要删除，后续更新仍需要它。若 codex 不在 PATH，可让安装助手定位 Desktop 捆绑的 CLI。

更新、回退与卸载

下载新包，在新目录解压校验，先备份当前配置与安装目录，再按上述命令更新同一个 marketplace。同名 marketplace 不允许直接换目录：旧路径已备份后，先用 codex plugin marketplace remove human-writer-local --json 移除旧来源登记，再立即登记新目录并安装；失败则重新登记旧来源。不要同时启用两个来源的 Human Writer。更新不迁移、不删除作品与本机状态。

卸载用 codex plugin remove human-writer@human-writer-local；另行移除已确认属于本插件的两个 hook 信任项。作品和状态保留。回退时从备份恢复旧包、重新注册并核对 hash，按需恢复 Human Writer 配置项；不要用整份旧配置覆盖更新后其他插件的配置。状态格式不兼容时先停止。

子 agent 与离线交接

除选题和无作品单次使用外，各槽位默认交给不继承主会话对话的子 agent；主会话负责提交、开卡和与你沟通。宿主派不出子 agent 时会说明并回退。成功提交记下执行者，正文自查与成品自查报告开头会显示。

要把这一步交给别的模型，直接说“这一步自查交给 Claude Code”。插件在作品的 handoffs/<执行编号>/ 生成 TASK.md、in/ 和 out/，输入与素材已复制。对方不需要安装插件。

  1. Claude Code 或 Devin CLI：在交接目录开会话，说“按 TASK.md 做”。只说“给 Devin”时按 Devin CLI 说明；网页版或转到云端执行时，上传整个目录。
  2. 把对方的产出放回交接包的 out/，回到主会话说“好了，请提交交接产出”。
  3. 提交后照常检查与确认；检查未通过，按原因修正同一个交接包的 out/ 再提交。让主会话派子 agent 修复时，会明确指定这个目录，附上失败原因，基于对方的产出修改。

交接去向只在当前对话有效；新会话需重新说明，但接管作品后可提交已经准备好的交接包。选题和无作品单次使用不支持交接。云端工具会收到包内素材，由作者决定是否交出。真实 Claude Code / Devin 接包效果仍待使用验证。

路线与反馈

输入 $human-writer 查看当前状态和六种用法；输入 $human-writer status 查看写作路线、每一步实际使用的技能、当前位置以及下一步在等谁。导入稿件会标明前面阶段未经过，定稿后显示 Word 与演示两条成品线的进度。

六种入口分别是：从题目写一份新材料、改一份已有的稿子、按新思路重组整篇、定稿后做成 Word 或演示、看看有哪些写法、记个反馈。它们是同一插件的使用方式。

记下不顺的地方

记个反馈：这次成品自查没有指出标题太长，打开后才发现换行。

模型在项目根目录的 human-writer-feedback.md 追加原话、作品和执行定位、结构性现象及自查是否发现。反馈不抄正文、素材和成品文字或数字。最后一次“已交出”之后累计五条，会提醒交给维护者；不会自动外发。

02 · 从题目开始

  1. 在 Codex 中打开一个专用目录。
  2. 发送下面的命令，创建作品。
$human-writer new 邻里旧书交换说明
  1. 把事实笔记、数据或引用材料放入返回的 works/<slug>/materials/。插件只记录素材清单与 hash，模型按需要读取；大 PDF 或表格不保证全部读完。
  2. 说“用 Human Writer 处理当前作品”。agent 会先确认读者、目的、材料与本篇写作标准，再生成 brief.md 与 outline.md。
  3. 在“确认框架”卡上选择“确认，开始写稿”或“重新梳理”。不回答即可暂放，之后能恢复卡片。
  4. 查看正文和 【待补：…】，完成自查与定稿。

缺资料时先标待补。你可以在定稿卡上选“补充内容”，再给出新素材和修改要求。本页“邻里旧书交换说明”为独立虚构示例，不对应真实活动或用户作品。

03 · 修改已有稿件

把源稿放入当前项目，例如 source.md，再发送：

$human-writer import source.md

源文件保持只读。工作正文在 works/<slug>/draft.md，之后在这份文件上阅读和修改。

  1. 先确认本篇写作标准；已有确认且仍适用的标准可以沿用。
  2. 做一次自查；有意见就修改一次，修改者自检；没有意见直接交稿。
  3. 交稿后等待你的决定。可补要求再改、用 go review 再审，或说“定稿”打开定稿卡。

已有明确修改要求时，可以直接说“按刚才的三条意见改”；在修改确认卡上选“修改（可以补内容、改判断）”“只改措辞”或“先不改”。

定稿卡的“继续修改”会先等待你的修改要求；“补充内容”回到写稿。升级前的旧采纳卡仍需在卡片里作答。

把意见整理成写作要求

requirements.md 记录标准 S、保持项 K、本轮目标 G。开工先对齐本篇适用标准，由作者确认后记录；已有确认且仍适用的标准可以沿用。它和素材归作者维护，插件只读。写下目标本身不会开始修订。

必须逐字保留的原文，在 K 条目里用「」标出，标点和空格也照原文复制。只检查基准稿中确实存在的引文；不存在的会列为跳过。

请按 requirements.md 的 G1 修订，保持 K1 不变；缺少依据的地方标为待补，不编造数据。

在修改确认卡上选择内容修改或只改措辞。卡片冻结这轮要求；后续编辑要求文件不会悄悄改变已经确认的范围。也可以由作者显式使用 go draft 或 go polish，再给出要求。

修改一次后交稿

路线 Review 有意见时，把全部意见交给写稿者修改一次，不再弹采纳卡。素材冲突按素材处理；只有作者能决定的问题写为待补或未改，集中在交稿时交代。不自动做第二次 Review。

已有明确作者要求的修改轮，完成后也默认交稿。要再审可用 go review；只想看独立报告可用 $human-writer use report-check。新 Review 检查当前稿，不再承诺对上一版逐条跟踪。升级前的旧卡和旧执行按原授权处理。

按新框架重组整篇

先把新主线写进写作要求的“必须保持”，然后回到框架：

$human-writer go outline

如果还没有选题，先用 go topic。确认新框架后，插件按框架重组现稿，保留事实、限定与必要关系，并逐节写明原有内容的去向。确认框架前，可以要求重新梳理。

单独使用一个技能

$human-writer use report-check
只检查当前作品是否符合写作要求，先给我报告，不推进写作阶段。

作品内执行会保留产物与记录，完成后阶段不变。独立写稿或润色的正文先成为候选，由作者选择采用、保留当前稿或手工处理；独立自查保留报告。

成品槽位不支持独立试做；请先定稿，再说“做成 Word”或“做成演示”。

没有打开作品时，use 只提供技能指令，由 agent 按你给的内容处理，不建立作品历史，也不能据此声称插件执行已经完成。

“这次用某个技能”只影响一次执行；“把本作品的自查绑定为 report-check”会保存到作品；skills 的列出与推荐只读，不会自动替换绑定。

导入 Word 稿件

导入仍只接受项目内 UTF-8 文本。先用文档工具把 DOCX 转成 Markdown，再导入；核对原文档的表格、批注与图片位置。原 DOCX 可放入素材目录留作来源。定稿之后，使用下面的成品流程生成新的 Word。

定稿后，交付 Word 与演示

  1. 完成正文，在定稿卡上选择“只定稿”。成品使用这个固定版本，不会把后续未定稿的编辑混进去。
  2. 说明“做成 Word”或“做成演示”。Word 先给图文方案；演示先给主线、页纲和原文章节去向。
  3. 查看方案文件，必要时自行编辑；卡上选择“确认，开始制作”或“重新做方案”。重做方案后，先说明要怎么改。
  4. 模型使用宿主已有工具制作，并尽量逐页渲染。Word 包含图源 HTML；演示包含自包含 HTML 和可编辑 PPTX。
  5. 成品自查对照正文、方案与成品，区分内容失真、版面问题和正文自身问题。有可处理意见时，选择“采纳后重新制作”或“直接交付”；无意见直接交付。只涉及正文内容的意见需回正文处理，不在成品里擅自改意思。
用 Human Writer 把这份定稿做成演示。

演示完成后，另发一条：

再出一份 Word。

交付文件在哪里

在 works/<slug>/products/doc/ 和 products/deck/。文件按作品名保存，例如 邻里旧书交换说明.docx、邻里旧书交换说明.html、邻里旧书交换说明.pptx；图文方案、页纲与自查报告也保存在对应目录。

只调整成品呈现

第 2 页的要点减成两条。

模型沿用上一版成品，只改要求涉及的页，留下 changes.md。作者直接改过的成品不会被覆盖，新产物另存为 <作品名>.<执行编号>.new.pptx 等文件，并明确给出新旧路径。

正文又有变化

先修订正文，再重新定稿；已有成品保留，并标为需要核对。更新时沿用已经确认的方案；若方案的出处与新稿不符，先调整或重做方案。成品中的手改不会自动回写 Markdown。

看懂成品自查

呈现意见分为“取舍”“设计”“渲染”：取舍看该不该画、内容与图表是否匹配；设计看层级、关系和文字负担；渲染看字体、溢出与缩放等实际显示。标明“需改方案”的意见要回方案处理。检查环境无法渲染时会单独说明未检查范围，不当作作者环境的成品缺陷。

渲染与使用边界

不为制作成品自动安装软件。已有工具失败时会尝试其他可用方式；浏览器受沙箱限制时，宿主允许的话可请求作者批准渲染。两份演示均已生成、只有一份不能逐页渲染时可交付，但会说明未看过哪份及原因。两份均无法渲染或成品做不出来时停止并说明缺口。批准后的真实 Desktop 渲染仍待实际使用验证。

04 · 卡片、恢复与换会话

没看到卡片，或卡片收起来了

告诉 agent“没看到卡片，请恢复当前问题”。它应使用 human_writer_continue 的 resume 重新呈现原问题，不另造答案。空答和跳过不算同意。

换一个会话继续

在同一个项目目录输入 $human-writer open <作品 ID、slug 或标题>。接管成功后，旧会话的卡片失效。原会话还有操作进行时，等待约一分钟再试；这个时间是提示，不是精确承诺。

作者保存后出现候选稿

作者内容与模型产物发生冲突时，正文保留作者修改，模型结果转候选。候选卡上选择采用候选、保留当前稿或手工处理。选题、框架冲突则保留作者文件，模型产物另存 <name>.<run_id>.new.md，按提示比对。

定稿后想继续 / 想先跳到某阶段

直接说明正文修改要求，或输入 $human-writer go draft、go review、go polish。跳转后的写稿或润色会等待要求；修改后重新定稿，已有成品会标为需要核对。

编辑器保持旧内容时再次保存，可能把新稿覆盖回旧稿。先检查编辑器是否重新加载文件；已登记版本和移开文件可帮助找回内容，但不等于完整备份。详见边界。

05 · 操作速查

输入 作用
$human-writer 当前作品状态 / 入口提示
$human-writer new <题目> 新建作品，从选题开始
$human-writer import <路径> 导入项目中的稿件
$human-writer open <作品> 打开或接管已有作品
$human-writer go <阶段> 作者跳转：topic / outline / draft / review / polish / finalize
$human-writer skills 查看技能目录与可用情况
$human-writer use <技能 ID> 独立使用技能，不推进阶段
$human-writer end 结束本会话的作品绑定；不删除作品，也不等于定稿

字面输入 $human-writer 是已验证入口。Desktop 菜单入口的插入格式仍待实际使用补验。

06 · 选择写作技能

默认技能覆盖五个阶段。你可说“这一次用 dbs-ai-check 自查”，或“把这篇作品的自查技能绑定为 dbs-ai-check”。前者只影响本次，后者保存到作品绑定。

技能 阶段 验证状态
dbs-ai-check 自查可选 · 当前正文与本篇标准 样本验收通过；真实使用效果未验
humanizer-zh 默认润色 样本验收通过；真实使用效果未验
material-brief 选题 试用：已有工程与宿主样本，效果待验
material-outline 框架 试用：已有工程与宿主样本，效果待验
material-draft 写稿 样本验收通过；真实使用效果未验
pyramid-long-form 框架 暂不可用：契约更新后旧记录失效，待补验
md-report-summary 写稿 暂不可用：契约更新后旧记录失效，待补验
report-check有写作要求时自查默认 · 对照要求和素材样本验收通过；真实使用效果未验
doc-visual图文方案、Word 成品两个组合试用：已有样本，成品效果待验
deck-story页纲、HTML 与 PPTX 成品两个组合试用：已有样本，成品效果待验
product-check成品自查试用：已有工程与宿主样本，效果待验

11 个技能中，4 个样本验收通过、5 个试用、2 个暂不可用。试用不等于完全没测过：已有工程和隔离宿主样本，部分还有内容阅读或判定，但尚未登记为正式效果验收。样本通过不保证适合所有文体，也不证明模型输出长期稳定。技能、适配文本或契约变化会使旧验收失效；请通过版本更新获取，不要直接修改已安装副本来绕过检查。

07 · 0.4.1 的范围
